# Project Workflow v2 — Multi-Phase Loop Engine (v2.4)

> **Class-level skill** for managing projects with multiple phases, multiple agents, and multi-month timelines. Built 2026-06-17 from Tuấn Anh's "multi-month project workflow" requirement. Use this when the work is BIG (phases, not just tasks).
>
> **v2.4 UPDATE (17/06 11:30):** **VERIFY-BEFORE-DONE** elevate thành **system-wide HARD RULE** — áp dụng cho MỌI task (không chỉ trong Loop). Memory edits, file writes, skill updates, 1-shot work đều phải verify bằng evidence trước khi nói "xong". Anti-pattern: *"xong rồi"* mà chưa chạy lệnh verify = FAIL. User explicit feedback: *"anh thích em khi làm việc phải verify, qa, test trước khi xác nhận task done!"*
>
> **v2.3 UPDATE (17/06 11:15):** Mental model chính thức — **Fable-5 = 🏛️ CỐT LÕI/NỀN TẢNG** (always on, mọi task). **Loop = ⚔️ VŨ KHÍ** cho dev/project work (dùng khi cần). Em tự động nhận biết khi nào dùng cái nào. User explicit feedback: *"fable cho toàn bộ và loop cho các công việc dev, hoặc em tự động nhận biết khi nào nên dùng cái nào, đại khái thì anh muốn fable 5 là cái cốt lõi và là nền tảng của hệ thống và loop là vũ khí!"*
>
> **v2.2 UPDATE (17/06 11:00):** Retry policy rõ ràng — FAIL → loop lại **Step 3** (không phải Step 0/1), max 3 attempts → ESCALATE. User explicit feedback: *"Ở bước thứ 6 if fail thì phải lặp lại loop từ bước 3 trở đi. Nếu vẫn fail đến lần thứ 3 thì report lại với orchestrator và chờ lệnh tiếp theo!"*
>
> **v2.1 UPDATE (17/06 10:55):** RESEARCH giờ là bước **BẮT BUỘC** trước PLAN (Step 0) và trước EXECUTE (Step 1.5). Loop giờ 6 bước thay vì 4. User explicit feedback: *"kỹ năng research là một kỹ năng bắt buộc và rất quan trong nhưng sao hầu hết trong các patterns, loop và workflow lại không có bước này!"*

## When to Use

Apply this workflow when ANY of these are true:
- Project timeline > 2 weeks
- > 3 phases
- > 5 agents involved
- Multi-month + multi-role
- User says "track phases", "log every action", "verify before next", "auto-execute plan"

**DO NOT use for:**
- 1-shot tasks (research 1 topic, fix 1 bug)
- Single-file edits
- Quick Q&A conversations
- 1-time setup tasks

## The 4-Layer Structure (with research/ sidecar)

```
wiki/projects/{project-id}/
├── hub.md              # Project overview, KPIs, team, current status
├── phases/             # Layer 1: Giai đoạn lớn (2-4 tuần/phase)
│   └── phase-{N}-{name}.md
├── research/           # Layer 1.5: Research outputs (BẮT BUỘC v2.1)
│   └── {task-id}-research-{date}.md
├── tasks/              # Layer 2: Task trong phase (1-3 ngày/task)
│   └── task-{phase}-{id}-{name}.md
├── actions/            # Layer 3: Action nhỏ (1-8 giờ/action)
│   └── {YYYY-MM-DD}-{task-id}-{action}.md
├── decisions/          # Quyết định quan trọng
│   └── decision-{id}.md
└── logs/               # Auto-generated by session-auto-log hook v2
    └── {YYYY-MM-DD}-sessions.md
```

## The 6-Step Loop Engine (v2.1 — RESEARCH BẮT BUỘC) + v2.2 Retry Policy

```
0. RESEARCH  → Orchestrator assign research-lead, output research/ folder
1. PLAN      → Tạo task file với YAML + deliverables + verify + research_refs
1.5 RESEARCH → Owner role inline research trước execute (conditional)
2. EXECUTE   → Owner role làm + log mỗi action
3. VERIFY    → qa-agent check PASS/FAIL (objective criteria)
4. NEXT      → PASS → next. FAIL → fix → loop Step 3 (max 3 attempts). Fail lần 3 → ESCALATE Telegram, chờ lệnh.
```

### v2.2 Retry Policy (NEW)

**Mỗi task PHẢI có 3 fields bắt buộc trong frontmatter:**
```yaml
verify_attempts: 0       # Counter, max 3 trước escalate
last_failure_reason: ""  # Lý do fail gần nhất (để quyết retry vs escalate)
escalated_at: null       # Timestamp khi escalate (null nếu chưa)
```

**Retry flow:**
```
Attempt 1: EXECUTE → VERIFY (FAIL) → if "có thể fix" → fix → Attempt 2
Attempt 2: EXECUTE → VERIFY (FAIL) → if "có thể fix" → fix → Attempt 3
Attempt 3: EXECUTE → VERIFY (FAIL) → **ESCALATE** → 🚨 BLOCKED → Telegram → CHỜ LỆNH
```

**⚠️ Quan trọng: Loop lại từ Step 3 (re-verify) SAU KHI owner fix — KHÔNG loop từ Step 0/1.**

**Khi nào RETRY (FAIL có thể fix):**
- Content issue (thiếu sources, dates cũ, voice lệch)
- Format issue (YAML thiếu, wikilinks ít)
- Citation issue (thiếu URL, date format sai)
- Minor logic (số liệu chưa verify, edge case)

**Khi nào ESCALATE NGAY (không retry):**
- Structural issue (thiếu permissions, API down, missing data)
- Scope creep (task definition sai từ PLAN)
- Dependency not ready (task trước chưa xong)
- Gate decision (cần Tuấn Anh quyết)

### Step 0: RESEARCH (BẮT BUỘC khi nào)

**Trigger conditions:**
- ✅ Tạo project mới (research về domain, audience, competitors)
- ✅ Tạo phase mới (research trends, algorithm, market)
- ✅ User yêu cầu explicit
- ❌ SKIP: phase kế tiếp đã có research file
- ❌ SKIP: operational task
- ❌ SKIP: user explicitly says "skip research"

**Output:** `research/{scope}-research-{YYYY-MM-DD}.md` với ≥2 independent sources, dates ≤30 ngày.

### Step 1: PLAN (sau Step 0)

Tạo task file với YAML frontmatter, deliverables, dependencies, owner_role, verify criteria. **PHẢI reference research file qua `research_refs` field.**

### Step 1.5: RESEARCH (BẮT BUỘC trước EXECUTE — conditional)

**Trigger conditions:**
- ✅ Task nội dung thay đổi so với research ban đầu
- ✅ Có decision point lớn (chọn A vs B cần data)
- ❌ SKIP: operational task (post video, send file)
- ❌ SKIP: time-critical (overhead research miss deadline)

**Output:** Action file inline `actions/{date}-{task-id}-pre-research.md` (≤30 phút research).

### Step 2-4: EXECUTE → VERIFY → NEXT (giống v2.0)

**Verify criteria (default — override per task):**
- [ ] Research đầy đủ (Step 0 + Step 1.5 nếu applicable)
- [ ] All deliverables present
- [ ] Each deliverable has source URL + date
- [ ] YAML frontmatter valid (incl. `research_refs` field)
- [ ] ≥2 wikilinks per wiki file
- [ ] Voice compliance (check against project voice profile)
- [ ] TRÁHN: 0 violations
- [ ] Citations format: title + URL + date

## State Machine (v2.2 — 3 retry attempts before escalate)

```
        ┌─────────┐
        │  TODO   │
        └────┬────┘
             ↓
   ┌─────────┴──────────┐
   │  RESEARCH (Step 0) │  ← BẮT BUỘC trước PLAN (v2.1)
   └─────────┬──────────┘
             ↓
        ┌─────────┐
        │ PLANNED │
        └────┬────┘
             ↓
   ┌─────────┴──────────┐
   │ RESEARCH (Step 1.5)│  ← BẮT BUỘC trước EXECUTE (conditional)
   └─────────┬──────────┘
             ↓
        ┌─────────┐
        │IN_PROG  │ ← attempt 1 (verify_attempts: 0)
        └────┬────┘
             ↓
   ┌─────────┴──────────┐
   ↓                    ↓
┌────────┐         ┌──────────┐
│AWAIT_  │         │ ESCALATE │ ← fail attempt 3 OR structural issue
│VERIFY  │         └──────────┘
└───┬────┘
    ↓
┌────────┐
│ PASS   │ → ✅ DONE → next
└────────┘
   OR
┌────────┐
│ FAIL   │ ← attempt 1 (verify_attempts++ → 1)
│        │ if "có thể fix" → back to IN_PROG (attempt 2)
│        │ if "structural" → ESCALATE
└────────┘
        ↓
        ┌─────────┐
        │IN_PROG  │ ← attempt 2 (verify_attempts: 1)
        └────┬────┘
             ↓
        AWAIT_VERIFY
             ↓
        ┌────────┐
        │ PASS   │ → ✅ DONE
        └────────┘
           OR
        ┌────────┐
        │ FAIL   │ ← attempt 2 (verify_attempts++ → 2)
        │        │ if "có thể fix" → back to IN_PROG (attempt 3)
        │        │ if "structural" → ESCALATE
        └────────┘
                ↓
                ┌─────────┐
                │IN_PROG  │ ← attempt 3 (LAST, verify_attempts: 2)
                └────┬────┘
                     ↓
                AWAIT_VERIFY
                     ↓
                ┌────────┐
                │ PASS   │ → ✅ DONE
                └────────┘
                   OR
                ┌────────┐
                │ FAIL   │ ← attempt 3 (verify_attempts++ → 3)
                │        │ **MANDATORY ESCALATE** → 🚨 BLOCKED → Telegram
                │        │   → set escalated_at → CHỜ LỆNH Tuấn Anh
                └────────┘
```

**Rule of thumb:**
- Verify attempts counter (`verify_attempts`) tracks retries
- Max 3 attempts before mandatory escalate
- Each retry loop: fix → re-verify (loop from Step 3, NOT Step 0/1)
- Escalate immediate nếu FAIL do structural issue

## CI Gate Script (v2.2 — 9 checks, was 8 in v2.1)

```bash
bash ~/.hermes/scripts/check-project-compliance.sh [project-id]
# Without arg: check all projects
# With arg: check specific project
```

Checks 9 things:
- [ ] `hub.md` exists
- [ ] All phases have files
- [ ] All tasks have `status` field
- [ ] All tasks have `owner_role` field
- [ ] All active tasks (status != TODO) have `research_refs` field ← **v2.1**
- [ ] `research/` folder exists (warn if missing) ← **v2.1**
- [ ] All tasks have `verify_attempts` field ← **v2.2**
- [ ] No tasks stuck FAILED > 24h (warn, should escalate) ← **v2.2**
- [ ] All actions have parent task reference (`task_id`)

Exit 0 = PASS, non-zero = FAIL with specific issues.

## Dashboard + Dependency Graph Pattern (added 17/06 22:18)

Mỗi project PHẢI có 2 file dashboard cập nhật live, không phải chỉ hub.md tĩnh:

### 1. `dashboard.md` — Single-page status cho Tuấn Anh

**Mục đích:** Anh nhìn 1 phát biết: tasks nào done/in-progress/blocked, recent actions, top picks, issues.

**Sections bắt buộc:**
- 🚦 Project Health (live metrics: tasks DONE/IN_PROGRESS/BLOCKED, action log count, research output count, verify pass rate)
- 📍 Phase Status (bảng: phase → task → status → owner → output)
- 📚 Research Outputs (link tới research/ files + highlights)
- 📝 Recent Actions (last 7 days, từ actions/ folder)
- 🔗 Dependency Graph (ASCII art: task → task relationships)
- ⚠️ Issues & Blockers (open + resolved)
- 🎯 Next Actions (recommend order)
- 🔄 Loop Engine Status (step nào đang chạy)
- 📊 Workflow Compliance (chạy `check-all-compliance.sh` output)

**Auto-update trigger:** Mỗi khi task status đổi → update dashboard. KHÔNG để dashboard stale.

**Pitfall:** Đừng build dashboard với fake data — chỉ tổng hợp từ files có thật (research/, actions/, tasks/).

### 2. `dependency-graph.md` — Task-level relationships

**Mục đích:** Biết task A fail thì ảnh hưởng task nào, parallel opportunities ở đâu, critical path bao lâu.

**Sections bắt buộc:**
- 🏗️ Phase-level graph (ASCII tree)
- 🔗 Phase Dependencies (bảng: depends on / blocks)
- 📋 Task-level Graph (ASCII cho mỗi phase với status: DONE/TODO/BLOCKED)
- 📊 Task Dependency Matrix (depends_on / blocks / can_run_parallel / status)
- 🎯 Critical Path (longest chain estimate)
- ⚡ Parallel Opportunities (group tasks có thể chạy song song + time saved)
- 🔥 Impact Analysis (if this fails → then these are blocked)
- 🔁 Cross-phase Dependencies (future)

**Update rule:** Mỗi task mới PHẢI khai báo 4 fields trong frontmatter:
```yaml
depends_on: [T-XX.Y, ...]
blocks: [T-XX.Z, ...]
related_tasks: [T-XX.W]    # Parallel/informs
research_refs: [T-XX.V]    # Output từ research task
```

**Verify:** `bash check-project-compliance.sh {project-id}` — fail nếu task active thiếu `depends_on` + `blocks`.

### Khi nào tạo 2 file này

- **Dashboard:** Tạo NGAY khi tạo project (song song với hub.md). Update mỗi task status change.
- **Dependency graph:** Tạo SAU khi có ≥3 tasks trong phase. Update khi thêm task mới hoặc thay đổi dependency.

## v2.4 Changes — VERIFY-BEFORE-DONE as System-Wide HARD RULE

**User explicit feedback (17/06 11:30):** *"Add thêm anh thích em khi làm việc phải verify, qa, test trước khi xác nhận task done!"*

### The HARD RULE (v2.4)

> **No task is "done" until verified with evidence.**
> Evidence = command output, test pass, file stat, MD5, exit code, count.
> Anti-pattern: *"xong rồi"* mà chưa chạy lệnh verify = **FAIL**.

### Where it applies (system-wide, not just Loop)

| Context | Before v2.4 | After v2.4 |
|---------|-------------|------------|
| Loop Engine task (project work) | Verify at Step 3 | Verify at Step 3 (UNCHANGED) |
| Memory edits (`memory` tool) | Trust the tool response | Re-read MEMORY.md after edit, confirm entry exists |
| File writes (`write_file`, `patch`) | Trust exit code | `grep` / `cat` to confirm content |
| Skill updates (`skill_manage`) | Trust return value | Re-read SKILL.md, confirm patch applied |
| Cron job edits | Trust JSON write | Re-parse JSON, confirm job present |
| Hook registrations | Trust gateway log | `tail gateway.log \| grep "Loaded"` |
| 1-shot tasks (research, conversation) | Optional verify | Verify before "xong" |
| Subagent outputs | Trust summary | Re-read actual artifact when possible |

### The 5-Command Verification Recipe (memorize this)

```bash
# 1. File existence + size + mtime
ls -la /path/to/file && stat -f "%Sm %z %N" /path/to/file

# 2. Content identity (if comparing)
md5 /path/to/source /path/to/mirror

# 3. Format validity (if applicable)
python3 -c "import yaml; yaml.safe_load(open('/path/to/file'))"

# 4. Count + completeness
grep -c "expected_marker" /path/to/file
wc -l /path/to/file

# 5. Side-effect check
ls -t /path/to/output/ | head -5
```

**5 commands = 2 minutes. ALWAYS run before claiming done.**

### Evidence Pattern in Reports

When reporting "done" on ANY task, include the verification evidence inline:

```
✅ DONE — verified

[File path] (size B, mtime HH:MM)
[Verify command] → [output]
[Exit code]
[Per-line evidence if applicable]
```

**Bad:** *"Updated memory file with work-style preference"*
**Good:** *"Memory updated: ~/.hermes/memories/MEMORY.md, `grep work-style` returned 1 match with verify rule, before/after chars: 2,489 → 1,919 (consolidated 5 stale entries), exit 0"*

### Failure mode this rule prevents

**Common anti-pattern (caught 17/06):** Em says *"đã update memory"* sau khi gọi `memory` tool. Tool returned success. Em announces done. Reality: memory was at 100% capacity → tool silently dropped the entry → no error → em never knew.

**With v2.4 rule:** Em MUST `grep` MEMORY.md after edit to confirm entry exists. If grep returns 0 matches → em catches the silent failure → fix (consolidate stale entries, retry).

### Bash→Python Hook Wrapper Pattern (NEW pitfall)

**Anti-pattern caught 17/06:** Wrapper dùng Python heredoc với bash variable interpolation — silent failure khi output có quotes/special chars.

**Fix (env vars > heredoc):**
```bash
#!/bin/bash
set -e
HOOK_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"

while [[ $# -gt 0 ]]; do
  case "$1" in --event) EVENT="$2"; shift 2;; --output) OUTPUT="$2"; shift 2;; *) shift;; esac
done

export HOOK_EVENT="$EVENT" HOOK_OUTPUT="$OUTPUT" HOOK_DIR
exec python3 << 'PYEOF'
import sys, os
sys.path.insert(0, os.environ.get('HOOK_DIR', '.'))
from handler import handle
context = {
    'message': os.environ.get('HOOK_OUTPUT', '')[:500],
    'response': os.environ.get('HOOK_OUTPUT', '')[:1000],
    'project_id': os.environ.get('HOOK_PROJECT', ''),
}
handle(os.environ.get('HOOK_EVENT', 'agent:end'), context)
PYEOF
```

**Reasoning:** `<< 'PYEOF'` (quoted heredoc) prevents bash interpolation INSIDE Python — but env vars still flow from bash → Python. Avoids 3 classes of bug:
1. Quotes in user output break heredoc parsing
2. Multi-line strings with special chars corrupt Python source
3. Newlines in `$OUTPUT` mess up the inline code
