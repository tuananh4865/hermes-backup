# Mode 8 Recurrence — H26 at 20:01 (the second H26 of 2026-06-24)

> **The same failure twice in one day.** The 19:30 H26 incident is documented in `h26-silent-kill-mode.md`. This file documents the 20:01 H26 incident — same mode 8 failure, same agent, same day, ~30 minutes later. The fact that the agent re-violated the rule after the skill was already loaded (during the 19:30 incident post-mortem) is the strongest possible evidence that the skill needs a stronger trigger signal.

## What happened

**Setup (continuing from 19:30 H26):** After the 19:30 incident (3 failed patch attempts, agent stopped, delivered in response only, then auto-fixed 12 perm regressions), the agent loaded `multi-agent-heartbeat` to understand the failure and verify the auto-fix was complete. The skill's `h26-silent-kill-mode.md` was read, the Mode 8 protocol was confirmed, and the system continued.

**30 minutes later, the cron fires again (20:01 H26).** Same orchestrator prompt: "30-minute heartbeat check. Actions: (1) Read state.md of all 5 active profiles...".

**What the agent did this time:**
1. Read 5 profile state.md files in parallel (correct per Step 1)
2. Ran `ls -d profiles/*/pending profiles/*/handoffs` (correct per Step 2)
3. Ran `find` for `pending*` and `handoff*` matches (correct per Step 2)
4. Ran `stat` on profile state.md files (correct per Step 1 freshness check)
5. Verified `~/.hermes/config.yaml` 600, `auth.json` 600, etc. (correct per security regression watch)
6. **WROTE a new H26 row to `qa-agent/state.md` (~2KB, file size 46162 → 48328 bytes)**
7. Delivered the heartbeat report in the response

**What the agent should have done per Mode 8:**
1. Same 1-5
2. Check: "Last row says '25th consecutive idle sweep' — 25 ≥ 20 boundary"
3. Check: "Any new security regression?" — No
4. Check: "Any agent conflict?" — No
5. Check: "Any new maker activity?" — No
6. Check: "Any outputs awaiting QA?" — No
7. **DO NOT WRITE A NEW ROW**
8. Deliver in response only

## The meta-failure (why this matters)

The skill content was **correct** at 20:01. The `h26-silent-kill-mode.md` reference was already there from the 19:30 incident. The agent had already read it once that day. The 6-condition check from Mode 8 would have returned "all zero, do not write" in 3 seconds.

**Yet the agent wrote the row anyway.**

The most likely explanation: the cron prompt did not include "load `multi-agent-heartbeat` before acting". The agent went directly to Step 1 (parallel read) without checking the skill. The patch it wrote then duplicated information that already existed in the H25 row ("system idle", "no security regressions", "no conflicts").

## What this proves

**Skills don't enforce themselves.** A skill with 100% correct content can still be ignored if:
1. The trigger to load it is not embedded in the workflow (e.g. "any cron prompt matching X must load this skill first")
2. The pre-write self-check is not made mandatory by the system reminder mechanism
3. The LLM's "always produce" bias is not explicitly countered at every sweep

**The fix (encoded in the SKILL.md trigger section):** Add a prominent `🚨 LOAD THIS SKILL ON ANY CRON PROMPT THAT SAYS "30m heartbeat"...` banner immediately under the "Don't use when" list. Make the load instruction impossible to miss.

**The secondary fix (not yet implemented):** Consider adding a system-level hook that detects "heartbeat" or "state.md" in the cron prompt and injects a reminder to load `multi-agent-heartbeat`. This is outside the skill's scope but is the right architectural fix.

## Pattern for future H_N+1 sweeps

If you are about to write a new sweep row and:
- The last 5+ rows all say "Nth consecutive idle sweep" where N ≥ 20
- You have already written 20+ rows to the same file today
- The file is >30KB
- The cron prompt does not require a new write

**Then:** Stop. Run the 6-condition check from Mode 8. If all zero, deliver in response only.

The most likely failure mode at H27+ is the agent reading the prior H26 row and copying its format. This is the exact pattern documented in the H23 lesson — "the H21 row's verbose narration was the default pattern, self-reinforcing". The fix is to **not start a new row in the first place**.
