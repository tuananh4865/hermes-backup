# Multi-Agent Heartbeat

> **The recurring 30m (or periodic) orchestrator health-pulse across N specialist profiles.**
> When the system has multiple specialist profiles (qa-agent, engineering-lead, operations-manager, code-reviewer, security-engineer, ...) and a cron fires the orchestrator to "check the system", this is the protocol.

**V24 (2026-06-30 12:45+, RE-VALIDATED 14:03 — silent-recovery bug, 3rd verification layer):** V23 caught log-mtime-vs-DB; the DB itself can also lie. `t_3a73b0af` shows `status='done'`, `completed_at=2026-06-30 12:34:36` (run 34), and run 34's metadata claims artifact `~/.hermes/kanban/workspaces/t_3a73b0af/youtube-channel-research-final.md` — but the workspace dir is empty (0 files). Same root cause as the original 2026-05-29 22:23 block (run 24 was `done` in DB but artifact never persisted). The kanban dispatcher records artifact paths in `task_runs.metadata` JSON before verifying `os.path.exists + size>0`. Parent-task auto-completion can flip a task to `done` based on child-task completion alone, without the parent's own final artifact being written. **Re-validated at 14:03 heartbeat (2nd sweep, 28m later):** ops-manager's 12:00 audit re-claimed "1 STUCK t_3a73b0af" → V23 recipe confirmed DB=done → V24 disk check confirmed workspace empty (silent-recovery persists). **V26 (2026-06-30 17:02 ICT, orchestrator 30m heartbeat — "status=ok but last_run=stale" missed-tick detection gap):** 5 daily/nightly crons (Autoresearch, X Research, Wiki Health, Memory Curator, Nightly Reflection) all showed `Last run: <stale date>  ok` — last execution was 2026-06-29, today's 2026-06-30 tick was missed, but H38's decision matrix classified them all as HEALTHY because status was `ok`. The gap: `hermes cron list` records only `last_run` + `last_exit_status`, not `next_expected_run` or `missed_count` — the scheduler has no concept of "should have fired by now". A 25h-stale daily cron is its own failure mode, distinct from "ok" (healthy) and "error" (failed). **V26 rule:** always compute `age_hours` against the schedule's natural interval (1h for `*/30`, 7h for `*/6`, 25h for daily/nightly) and flag any cron where `age > threshold`. **Detection recipe + decision matrix + false-positive guard:** `references/v26-ok-but-stale-missed-tick.md`. **v1.26.0 update:** H38 decision matrix in `quick-reference-6check.md` Check 2 needs a 4th row ("`Last run: <stale>  ok` → ⚠️ MISSED TICK"); applied in this patch. Common cause in Tuấn Anh's setup: Mac sleep during the 02:00-08:00 window silently skips all jobs scheduled in that range. Recovery is automatic at next natural fire (tomorrow 02:00/04:00/07:00/etc.) — only intervene with `hermes cron run <id>` if user explicitly wants today's missed output.

**V27 (2026-06-30 18:05 ICT, H78 sweep — `pmset` root-cause confirmation for V26 missed-tick windows):** V26 detected 5 missed crons in the 2026-06-30 02:00-07:30 window (Autoresearch, X Research, Wiki Health, Memory Curator, Wiki Memory Forget). H78 sweep root-caused via `pmset -g log | grep "2026-06-30 0[2-7]:"` — Mac was in `PrevIdle` low-power state the entire window. Crucially, `Hermes Daily Backup` (Schedule `0 3 * * *`) DID fire at 03:05 because backup scripts include their own `pmset noidle` wrapper — the other 5 crons don't have wake-from-sleep handling. **Cron daemon self-recovery:** at 09:52:14, `~/.hermes/logs/agent.log` shows the cron daemon emitted "Job 'X' missed its scheduled time (..., grace=7200s). Fast-forwarding to next run: ..." for all 5 missed jobs. The `grace=7200s` (2h) patience window means **no manual `hermes cron run <id>` is needed** — scheduler fast-forwards to next natural fire automatically. **V27 recipe:** when V26 fires with multiple missed ticks in a contiguous time window, run `pmset -g log | grep "<date> 0[window]:"` to confirm `PrevIdle`. If confirmed → root cause is Mac sleep, not daemon/script failure → do NOT escalate as a Hermes fault, recommend user add `pmset noidle` or `caffeinate -d` wrappers to the 5 affected scripts. **v1.27.0 update:** V27 section added to `references/v26-ok-but-stale-missed-tick.md`; description updated to include V27.

**V28 (2026-06-30 19:30 ICT, H79 heartbeat — V27 auto-recovery prediction FALSIFIED):** At H79 (90min after V27 written, 12h+ after the original 02:00-07:30 misses), the same 5 crons STILL had `last_run = 2026-06-29T*` — they did NOT fast-forward within the day. The scheduler logged the "missed scheduled time, grace=7200s" warning at 09:52 but the fast-forward goes to the **NEXT scheduled occurrence**, not within hours. For a daily cron that missed today's 07:00, auto-recovery is tomorrow 07:00 — NOT today. **V28 rule:** `grace=7200s` fast-forward is to the NEXT scheduled occurrence, not within hours. **V28 update to V27 treatment:** recommend manual `hermes cron run <id>` if (a) the missed cron is user-critical (e.g. Autoresearch for daily research knowledge building, Wiki Health for wiki hygiene), OR (b) the same cron has missed 2+ consecutive ticks (H79 evidence — `pmset noidle` wrapper fix may be needed faster than "tomorrow auto-recovers"). Recipe + ground-truth table + verification recipe in `references/v26-ok-but-stale-missed-tick.md` § V28. **v1.28.0 update:** V28 section added to `references/v26-ok-but-stale-missed-tick.md`; description updated to include V28; V27's "no manual intervention needed" language softened to "non-critical AND user accepts next-day output".
